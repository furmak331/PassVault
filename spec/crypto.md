# PassVaultify crypto format, version 1 (`pvf1`)

This document is the source of truth for how PassVaultify derives keys and
encrypts data. Every client (TypeScript extension and web vault, Java CLI)
implements exactly this, and [`vectors/pvf1.json`](vectors/pvf1.json) pins the
expected outputs. The vectors are generated by an independent implementation
([`vectors/generate.py`](vectors/generate.py), using Python's `cryptography`
package), so a client that passes them agrees with something other than itself.

Only standard primitives are used: PBKDF2-HMAC-SHA256, HKDF-SHA256 and
AES-256-GCM. Nothing here is custom cryptography.

## Goals

- **Zero knowledge.** No server, in any storage mode, ever receives the master
  password, the master key, the vault key or any plaintext item.
- **Cheap password changes.** Changing the master password re-wraps one key; it
  does not re-encrypt the vault.
- **Tamper evidence.** Every ciphertext is authenticated, and bound to the
  thing it belongs to, so a server can't swap one item's ciphertext for another.
- **Crypto agility.** KDF settings are stored with each vault, so stronger
  settings (or Argon2id) can be adopted without breaking existing vaults.

## Encodings

| Data                                  | Encoding                                   |
| ------------------------------------- | ------------------------------------------ |
| Text (passwords, AAD, `info` strings) | UTF-8                                      |
| Master password                       | Unicode NFKC normalization, then UTF-8     |
| Binary values in JSON                 | base64url, no padding (RFC 4648 section 5) |
| Item IDs                              | lowercase UUID v4 strings                  |

NFKC normalization matters: "Å" typed as one code point (U+00C5) and as "A" plus
a combining ring (U+0041 U+030A) must unlock the same vault.

## Key hierarchy

```
master password ──PBKDF2-SHA256(salt, iterations)──▶ master key (32 bytes, never stored or sent)
                                                        │
                       ┌──── HKDF-SHA256, info "passvaultify/v1/auth" ──▶ auth key (32 bytes)
                       └──── HKDF-SHA256, info "passvaultify/v1/wrap" ──▶ wrap key (32 bytes)

vault key  = 32 random bytes, created once per vault
wrapped vault key = AES-256-GCM(wrap key, vault key, AAD "passvaultify/v1/vault-key")
item       = AES-256-GCM(vault key, item JSON, AAD "passvaultify/v1/item/" + item ID)
```

### 1. KDF settings

Stored with the vault in plaintext (they are not secret):

```json
{ "alg": "pbkdf2-sha256", "iterations": 600000, "salt": "<16 random bytes, base64url>" }
```

600,000 iterations is OWASP's current recommendation for PBKDF2-HMAC-SHA256.
The salt is 16 bytes from a cryptographically secure random generator, created
once per vault.

### 2. Master key

`masterKey = PBKDF2-HMAC-SHA256(NFKC(password), salt, iterations, 32 bytes)`

### 3. Auth key and wrap key

`HKDF-SHA256` (RFC 5869) with an empty salt, which RFC 5869 defines as 32 zero
bytes:

- `authKey = HKDF(masterKey, info = "passvaultify/v1/auth", 32 bytes)`
- `wrapKey = HKDF(masterKey, info = "passvaultify/v1/wrap", 32 bytes)`

The two keys are independent: knowing the auth key reveals nothing about the
wrap key. In self-hosted and cloud mode the client sends only the auth key at
sign-in, and the server stores `Argon2id(authKey)`. In local-only mode the auth
key is never used.

### 4. Vault key

32 random bytes, generated once when the vault is created. All items are
encrypted with it. It is stored only in wrapped form:

`wrappedVaultKey = seal(wrapKey, vaultKey, aad = "passvaultify/v1/vault-key")`

Unlocking is unwrapping: a wrong password produces a wrong wrap key, and
AES-GCM authentication fails. No separate password verifier is stored.

### 5. Items

`ciphertext = seal(vaultKey, UTF-8 JSON of the item, aad = "passvaultify/v1/item/" + itemId)`

Binding the item ID into the AAD means ciphertext moved to a different item ID
fails to decrypt. Item metadata needed for sync (ID, revision, updated time,
deleted flag) stays outside the ciphertext.

## Envelope format

`seal(key, plaintext, aad)`:

1. `iv` = 12 random bytes (never reused with the same key).
2. `ct` = AES-256-GCM encryption of `plaintext` with `iv` and `aad`, with the
   16-byte tag appended (the Web Crypto and JCE convention).
3. Output the string `pvf1.` + base64url(`iv`) + `.` + base64url(`ct`).

`open(key, envelope, aad)` reverses this. It must reject any envelope whose
prefix is not `pvf1`, whose IV is not 12 bytes, or whose tag doesn't verify.

## Vault fingerprint

`fp = HKDF(vaultKey, info = "passvaultify/v1/fingerprint", 16 bytes)`

- **Code:** the first 6 bytes of `fp` as uppercase hex in three groups of four,
  for example `7F3A 91C2 0E5B`.
- **Rings:** the ring pattern is drawn from
  `SHA-256(UTF-8("passvaultify/v1/rings/" + code))`, first 16 bytes (128 bits),
  read most significant bit first. Deriving it from the code means the lock
  screen can draw it from the vault header alone, before unlocking.

The fingerprint is computed when the vault is created and stored in plaintext
with the vault, so the lock screen can show it before unlocking. It reveals
nothing about the vault key. A phishing page on another origin can't read
extension storage, so it can't draw the user's fingerprint.

## Vault record (local-only mode)

```json
{
  "format": "pvf1",
  "kdf": { "alg": "pbkdf2-sha256", "iterations": 600000, "salt": "…" },
  "wrappedVaultKey": "pvf1.….…",
  "fingerprint": "7F3A 91C2 0E5B",
  "items": [
    {
      "id": "…uuid…",
      "revision": 3,
      "updatedAt": "2026-10-01T09:41:00Z",
      "deleted": false,
      "data": "pvf1.….…"
    }
  ]
}
```

## Changing the master password

1. Derive the old wrap key and unwrap the vault key.
2. Create a new salt, derive the new master key, auth key and wrap key.
3. Re-wrap the same vault key with the new wrap key.

No item is re-encrypted.

## Backup file

A backup is the vault exactly as it is stored, wrapped in JSON. Nothing is
re-encrypted, so a backup is exactly as strong as the vault: it opens with the
master password that was current when it was made.

```json
{
  "format": "passvaultify-backup",
  "version": 1,
  "exportedAt": "2026-10-02T12:00:00.000Z",
  "vaultName": "Home",
  "header": {
    "format": "pvf1",
    "kdf": { "...": "..." },
    "wrappedVaultKey": "pvf1....",
    "fingerprint": "7F3A 91C2 0E5B"
  },
  "records": [
    { "id": "...", "revision": 3, "updatedAt": "...", "deleted": false, "data": "pvf1...." }
  ]
}
```

- `vaultName` is optional and in plaintext, so the restore screen can say what
  it's restoring. Tombstones are left out.
- Readers reject the file unless every field is well formed. Iterations must be
  between 1,000 and 10,000,000: a backup is untrusted input, and a huge count
  would freeze the reader while "unlocking".
- Readers must unwrap the vault key and decrypt **every** record before writing
  anything. A wrong password or one altered record (AES-GCM rejects it) means
  nothing is restored.
- Restoring as a new vault keeps record IDs. Merging into an existing vault
  decrypts the items and re-encrypts them under the destination's vault key
  with new IDs, after rebuilding each item field by field.

## What this format does not cover yet

- Argon2id KDF (planned; `alg: "argon2id"` with `memory`, `iterations`,
  `parallelism`).
- Key rotation of the vault key itself.
- Sharing items between users (would need public-key wrapping).
